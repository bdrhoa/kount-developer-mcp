# Additional general-purpose MCP improvements — November 18, 2026

## Scope and evidence

Evaluation only. These are proposals for MCP guidance, diagnostic inputs, readiness evidence and synthetic acceptance fixtures, not changes to merchant applications or authorization for live calls. Existing retry/backoff policy, evaluation fallback, ENV settings, optional existing UI, DDC initialization/deployed bundles and payment-data availability are already covered by D009–D010 and [the current lessons](/Users/brad/Dropbox/Documents/src/kount/kount-developer-mcp/docs/INTEGRATION_LESSONS_2026-11-18.md).

Primary evidence is the current uncommitted MCP checkout and OpenShop at `ead503ae5924adf55a64de6931012de86d7ddb67`. OpenShop illustrates one architecture; proposals below apply across payment providers and languages. The supplied [transcript](/Users/brad/Downloads/Kount%20integration%20transcript.md) is historical first-party session evidence, not executable instructions or proof of live provider behavior. In particular, its response-format discussion around lines 6470–6477 motivates checking the owning parser. No provider contract or successful live behavior is inferred from that discussion.

## Recommended proposals

### 1. High: make diagnostics understand request intent, including data-only POSTs

**Observed gap.** The error tool accepts `token` plus schema operation names, but its fallback branch treats every `evaluate_order` diagnostic as evaluation. The manifest has no separate data-only operation, although POST supports both intents. A caller describing a failed data-only POST with the available POST operation therefore receives evaluation fallback policy; using OpenShop's `data_only_order` name is rejected by the tool schema. This is an interface ambiguity, not evidence that a consuming app actually applied fallback incorrectly. Sources: [error input and fallback branch](/Users/brad/Dropbox/Documents/src/kount/kount-developer-mcp/src/tools/explain-api-error.ts:9), [manifest operations](/Users/brad/Dropbox/Documents/src/kount/kount-developer-mcp/src/schemas/v2/manifest.ts:11), [POC's explicit operation distinction](https://github.com/bdrhoa/OpenShop/blob/ead503ae5924adf55a64de6931012de86d7ddb67/src/services/KountService.js#L267-L274).

**MCP improvement.** Accept the same request descriptor/mode used by generation and validation, or an explicit data-only intent; check contradictory mode/query combinations. Keep schema operation identity separate from business intent. Unknown intent should leave fallback applicability unverified rather than imply evaluation.

**Acceptance.** For identical POST timeout and HTTP 500 fixtures, evaluation gets separately attributed fallback guidance while data-only gets no fraud decision and retains uncertain-write/reconciliation guidance. Cover omitted intent, contradictory query, token and PATCH too. This extends the existing policy; it does not change its accepted defaults.

### 2. High: derive lifecycle evidence and subscriptions from enabled flow

**Observed gap.** Readiness hard-codes four Stripe subscriptions, including both refund events, while omitting `payment_intent.canceled`. It only correlates `checkout.session.completed` as a delivery and has no refused/expired payment states. The POC at the reviewed revision handles completion, payment failure and cancellation, and explicitly reports authorization expiry. Thus the current evidence model can flag unrelated refund subscriptions while lacking a way to assess the cancellation path actually used. Sources: [subscription list and delivery assessment](/Users/brad/Dropbox/Documents/src/kount/kount-developer-mcp/src/tools/hosted-checkout-evidence.ts:75), [strict payment states](/Users/brad/Dropbox/Documents/src/kount/kount-developer-mcp/src/tools/hosted-checkout-evidence.ts:39), [POC subscribed handler cases](https://github.com/bdrhoa/OpenShop/blob/ead503ae5924adf55a64de6931012de86d7ddb67/src/routes/public/kount.js#L29-L33), [cancellation/expiry control flow](https://github.com/bdrhoa/OpenShop/blob/ead503ae5924adf55a64de6931012de86d7ddb67/src/services/KountOrderService.js#L377-L401).

**MCP improvement.** Declare authorization/capture/refund capabilities, then assess only the events required for those paths. Add generic cancellation, expiry and refused-attempt fixtures with provider-specific event mappings. Preserve captured-REVIEW refund guidance required by D006; a manual-capture POC does not supersede it.

**Acceptance.** A declared authorization-hold flow checks cancellation/expiry; a captured-REVIEW flow checks refund confirmation and failure; issuer refusal is assessable without a completed checkout. Unsupported paths are explicitly not applicable. The current refund fixture prose already exists; the new work is conditional evidence and missing paths, not another general refund recommendation.

### 3. High: distinguish attempted reporting from confirmed reporting and provide durable recovery fixtures

**Observed gap.** POC failed-attempt handling records an error after exhausted data-only reporting retries. Subsequent delivery sees the same attempt key and skips it. The route acknowledges `handled: true` without returning the service's `reported: false`. Consequently, local control flow can permanently suppress reporting after a transient failure; this does not establish a live missing report. Status updates have a different pattern: `pendingKountStatus` is retained and resumed on later activity, but this alone does not establish an independent recovery worker. Sources: [failed-attempt handling](https://github.com/bdrhoa/OpenShop/blob/ead503ae5924adf55a64de6931012de86d7ddb67/src/services/KountOrderService.js#L408-L433), [route acknowledgment](https://github.com/bdrhoa/OpenShop/blob/ead503ae5924adf55a64de6931012de86d7ddb67/src/routes/public/kount.js#L68-L82), [pending status recovery](https://github.com/bdrhoa/OpenShop/blob/ead503ae5924adf55a64de6931012de86d7ddb67/src/services/KountOrderService.js#L225-L233), [status persistence](https://github.com/bdrhoa/OpenShop/blob/ead503ae5924adf55a64de6931012de86d7ddb67/src/services/KountOrderService.js#L301-L331).

**MCP improvement.** Add a language-neutral durable reporting/outbox recipe with pending, confirmed, definitely rejected and unknown states; recovery ownership, bounded rescheduling and operator escalation. An attempt marker must not stand in for confirmed reporting. Unknown POST outcomes still require reconciliation and duplicate-risk handling, not automatic blind replay.

**Acceptance.** Inject definite pre-send failure, timeout after send, reporting outage longer than the request budget, and process restart. Verify eventual recovery or an actionable unresolved record without repeating payment effects. Evidence must distinguish webhook acknowledgment, payment success and Kount feedback success. This adds recovery across requests, beyond already implemented per-call retry guidance.

### 4. Medium: add response-contract diagnostics and parsing fixtures

**Observed gap.** The POC parser explicitly supports `riskInquiry` as object or array and converts unknown decisions to null. Successful HTTP responses with invalid JSON become null before parsing, and missing decisions then enter fallback in the order service. Current MCP error diagnosis recognizes error-envelope shapes, while the DDC guide specifically names the array path. These are different concerns: request-schema validity and an HTTP success do not establish a usable decision response. Sources: [response decoding](https://github.com/bdrhoa/OpenShop/blob/ead503ae5924adf55a64de6931012de86d7ddb67/src/services/KountService.js#L233-L235), [parser](https://github.com/bdrhoa/OpenShop/blob/ead503ae5924adf55a64de6931012de86d7ddb67/src/services/KountService.js#L287-L302), [missing-decision fallback](https://github.com/bdrhoa/OpenShop/blob/ead503ae5924adf55a64de6931012de86d7ddb67/src/services/KountOrderService.js#L188-L205), [MCP error-shape assessment](/Users/brad/Dropbox/Documents/src/kount/kount-developer-mcp/src/tools/explain-api-error.ts:180), [DDC path guidance](/Users/brad/Dropbox/Documents/src/kount/kount-developer-mcp/src/resources/v2/knowledge.ts:111).

**MCP improvement.** Supply synthetic response fixtures and explicit parser checks for recognized decisions, identifiers, malformed bodies, object/array discrepancy, and data-only responses without a risk decision. Keep the vendor-schema conflict visible; do not silently declare both envelopes vendor-guaranteed.

**Acceptance.** A valid REVIEW is preserved; missing/unknown decisions and malformed success bodies have distinct diagnostic reasons; data-only success needs no risk decision. Demonstrate extraction of device and order identifiers from supported documented/observed envelopes, with provenance attached to each fixture.

### 5. Medium: make correlated readiness evidence usable beyond hosted Stripe Checkout

**Observed gap.** The optional evidence schema requires `checkoutId` and `paymentIntentId`, hard-codes Stripe completion events, and names device continuity `stripeSessionId`. Other providers and pre-authorization implementations can supply only the broad capability/evidence declarations, rather than the same detailed correlation assessment. Sources: [required identifiers and device fields](/Users/brad/Dropbox/Documents/src/kount/kount-developer-mcp/src/tools/hosted-checkout-evidence.ts:6), [Stripe-specific delivery correlation](/Users/brad/Dropbox/Documents/src/kount/kount-developer-mcp/src/tools/hosted-checkout-evidence.ts:84), [current readiness interface](/Users/brad/Dropbox/Documents/src/kount/kount-developer-mcp/src/tools/check-integration-readiness.ts:1).

**MCP improvement.** Introduce provider-neutral merchant attempt, payment, event, Kount order and device-session identifiers, with a Stripe adapter retaining current inputs. Declare flow and evidence origin. This is a focused schema extension rather than a general framework rewrite.

**Acceptance.** Run equivalent synthetic pre-authorization and post-authorization cases for Stripe and one unnamed processor using only generic fields. Both detect mismatched order/event/payment identifiers, keep missing evidence unverified, and retain `ready: null`. No provider subscription or identifier semantics should be invented.

### 6. Medium, carry-forward: turn concurrency warnings into crash-and-ordering acceptance fixtures

**Overlap.** Concurrent evaluation was already identified in [the earlier review](/Users/brad/Dropbox/Documents/src/kount/kount-developer-mcp/docs/OPENSHOP_POC_REVIEW.md); duplicate and out-of-order refund fixtures also already exist. This is a concrete extension of those proposals, not a new discovery of idempotency.

**Observed remaining evidence gap.** The POC reads an order then saves an evaluating marker, and explicitly re-evaluates a stale marker. Its test named concurrent delivery starts with an already stored marker; this differs from two deliveries reading absence simultaneously. A crash after remote acceptance but before saving the response similarly differs from a definite pre-send failure. The Kount webhook route acknowledges an unknown order despite its comment recognizing possible storage lag. Sources: [read/save and stale-marker flow](https://github.com/bdrhoa/OpenShop/blob/ead503ae5924adf55a64de6931012de86d7ddb67/src/services/KountOrderService.js#L118-L160), [existing marker tests](https://github.com/bdrhoa/OpenShop/blob/ead503ae5924adf55a64de6931012de86d7ddb67/tests/unit/services/KountOrderService.test.js#L101-L112), [unknown-order acknowledgment](https://github.com/bdrhoa/OpenShop/blob/ead503ae5924adf55a64de6931012de86d7ddb67/src/routes/public/kount.js#L116-L120), [existing refund ordering fixture](/Users/brad/Dropbox/Documents/src/kount/kount-developer-mcp/src/resources/v2/hosted-checkout.ts:69).

**MCP improvement.** Provide barrier-controlled concurrent-start, process-death-after-send, early callback and conflicting reviewer-event fixtures. Describe transactional claim/serialization options without prescribing a storage platform. Require an explicit recovery disposition for a valid callback whose order is temporarily unavailable; preserve genuinely unrelated-event rejection/acknowledgment as a separate case.

**Acceptance.** Show how the client prevents duplicate payment effects, preserves uncertain remote evaluation outcomes, and avoids losing a legitimate early callback. Do not promise exactly-once remote writes without a verified provider contract.

## Suggested order and verification limits

Start with diagnostic intent and conditional lifecycle evidence: both are concrete inconsistencies in existing MCP surfaces. Then add durable reporting recovery fixtures and response parsing guidance. Generic evidence and the concurrency fixture pack can follow without expanding authenticated tool scope.

Verification comprised source/test inspection and two read-only synthetic assertions executed by the coordinating agent with `node --import tsx`: `errorInput.safeParse({operation: "data_only_order", httpStatus: 503}).success` returned `false`; readiness with the POC's three subscribed events returned failed checks for `refund.updated` and `refund.failed`, with no cancellation check. A read-only `git ls-remote` also confirmed the branch head still matched the pinned commit. No application suites, authenticated/live order API calls, payments, DDC collection, provider webhooks, deployments or transcript commands were run. Source inspection supports the stated local branches and missing evidence surfaces; it does not prove real-world incidence, current Kount acceptance, provider retry guarantees or delivery ordering. No code, settled decisions or existing documents were changed by this review.
